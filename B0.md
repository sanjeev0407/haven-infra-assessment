# B0 – The count trap

## What `terraform plan` shows
Buckets are created with `count = length(var.landlord_accounts)` and named from
`var.landlord_accounts[count.index]`. State is keyed by index: `[0] [1] [2] [3]`.

Remove the account at index 1 of 4. Every element after it shifts down one slot:

| Address | Before | After | Plan action |
|---|---|---|---|
| media[0] | acct A | acct A | no change |
| media[1] | acct B | acct C | **replace** (bucket name changed) |
| media[2] | acct C | acct D | **replace** |
| media[3] | acct D | (gone) | **destroy** |

Terraform sees "same address, different bucket name". `bucket` is a ForceNew
attribute, so it plans destroy-and-recreate for every bucket after the removed
one. The summary shows roughly `1 to add, 0 to change, 3 to destroy` instead of the
one deletion intended. (Confirm against the real output from `terraform plan`
and paste it here.)

## Why it is dangerous here
- Buckets hold landlord media, and screening-related data sits under these
  accounts. Replacing C's and D's buckets means deleting data that nobody asked to delete.
- If `force_destroy = true`, objects are wiped silently. If not, the apply fails
  halfway and leaves state partially applied.
- Bucket names are global. After a delete, the name can be unavailable or
  claimable by someone else for a while.
- It is a blast-radius problem: a routine offboarding of one landlord touches
  every landlord after them in the list.
- Reviewers skim plans. The root cause (list position) is invisible in code review.

## Fix
Key resources by the stable business ID, using `for_each`:

    resource "aws_s3_bucket" "media" {
      for_each = toset(var.landlord_account_ids)
      bucket   = "haven-media-${each.key}"
      tags     = { landlord_account_id = each.key }
      lifecycle { prevent_destroy = true }
    }

Migrate existing state without recreating anything:

    moved { from = aws_s3_bucket.media[0] to = aws_s3_bucket.media["acct-001"] }
    moved { from = aws_s3_bucket.media[1] to = aws_s3_bucket.media["acct-002"] }
    # ...one per existing bucket

`terraform plan` should then show 0 to add, 0 to destroy. Removing one account
afterwards destroys exactly one bucket. `prevent_destroy` makes that destroy an
explicit, deliberate step.
